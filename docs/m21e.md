# M21e — Composable prescribed electric force and uniform gravity

## Capability, not a question-specific simulator

The same particle model now composes an existing `PrescribedField` with an
optional, immutable `UniformGravity`. The new `ConservativeForceSystem`
combines a typed `PrescribedElectricForce` and gravity; no example name,
exam number, callback, trajectory formula or separate integrator enters the
production solve. All examples use the existing adaptive vector controller,
source guards, prescribed-motion viewer and immutable M20b scenario interface.

The scope was committed in [the acceptance charter](m21e_charter.md) before
implementation. This is a deliberately bounded two-contribution interface,
not an unrestricted force-plugin registry or universal multi-domain engine.

    F_e = q E(r)
    F_g = m g
    F_total = F_e + F_g
    U_e = q V(r)
    U_g = -m g . (r - r_ref)
    H = K + U_e + U_g

Gravity is **not** implemented as an equivalent electric field. The electric
field and voltage observations remain the actual electrical quantities.
Changing mass therefore changes electric acceleration qE/m but not g;
changing charge changes electric force but not gravitational force. The
reference position fixes the zero of U_g only, not the launch or a guide.

## Author and revise a reusable model

```python
from conductor_sim import (
    PointCharge, PrescribedField, UniformElectricField,
    TestChargeMotionSpec, UniformGravity,
)
from conductor_sim.scenarios import (
    PrescribedScenario, revise_scenario, sample_scenario_viewer,
)

model = PrescribedScenario(
    scenario_id="oblique-electric-gravity",
    spec=TestChargeMotionSpec(
        field=PrescribedField((UniformElectricField((6., 0., 0.)),)),
        particle=PointCharge(1e-6, (0., 0., 0.)),
        mass_kg=2e-6,
        initial_velocity_m_s=(.4, 1.4, 0.),
        duration_s=.24,
        sample_interval_s=.01,
        plane_normal=(0., 0., 1.),
        length_scale_m=.5,
        gravity=UniformGravity((0., -10., 0.)),
    ),
    source_annotations=(("field:applied", "Applied electric field"),),
    provenance="Teacher hypothetical: independent horizontal E and downward g.",
)
heavier = revise_scenario(
    model, scenario_id="double-mass",
    note="Teacher hypothetical: double only the mass.",
    motion_changes={"mass_kg": 4e-6},
)
lower_g = revise_scenario(
    model, scenario_id="lower-gravity",
    note="Teacher hypothetical: halve only the gravity magnitude.",
    gravity_changes={"acceleration_m_s2": (0., -5., 0.)},
)
# Each call independently integrates the complete model. No baseline run is reused.
base_view = sample_scenario_viewer(model, extent_m=.5)
heavy_view = sample_scenario_viewer(heavier, extent_m=.5)
```

The original remains immutable. Actual normalized changes are recorded,
including gravity changes under stable identity `gravity`. Existing source
IDs persist. Active gravity reserves that ID; electric-only legacy source
names and scenario hashes are preserved. Both charge and mass edits recertify
the complete system.

`gravity_changes` patches an already authored component's acceleration or
reference position. It does not insert a new component into a legacy model:
a new baseline must explicitly declare gravity. A zero-acceleration gravity
component can be revised to nonzero acceleration within the same inventory.
The M20a comparison requires matching component membership, physical slices
and saved time grids; changing gravity direction can change the chosen
screen-up direction and make two otherwise valid runs incomparable. Such a
pair is refused rather than silently recentered or rotated.

## Source-backed JEE acceptance and transfer examples

The primary source is `02_conductors_half_size.pdf`, physical PDF page 15,
Archives Single Correct Q2, printed as **IIT-JEE 2012**. Its original full
workbook page was visually checked, without OCR. Exports verify its SHA-256:
`9dff3c02a9f1848d2c3d99cb1a6e7a44dc7f5a51f7a3a2b8cc92d10ce1fbca5d`.
This milestone's source inspection is the supplied workbook, not a new claim
of independently inspecting the official original paper.

The question gives a proton released from rest midway between two vertical
plates separated by 1 cm, moving at 45 degrees to vertical immediately after
release. Horizontal electric force and downward gravity give qE=mg, hence
X=mgd/q. With explicitly rounded constants m_p=1.67e-27 kg, e=1.6e-19 C,
g=10 m/s², the computed voltage is **1.04375e-9 V**, matching the 1e-9 V
option. The speed at t=0 is zero; 45 degrees describes the initial acceleration
and subsequent velocity, not a direction of a nonzero initial velocity.

The imposed uniform-gap field is an idealization. No plate geometry is solved,
no induced response to the proton is included, and no fringe, collision or
radiation model is supplied. The illustrative 0.024 s preview ends at
x=0.00288 m, strictly before the plate at x=0.005 m. A release from rest under
this constant resultant follows a straight diagonal spatial path; it is not
misrepresented as an oblique-launch parabola.

These examples demonstrate transfer between arrangements, not a statistical
claim of JEE Advanced coverage or automatic PDF interpretation. No new
production code is added per case.

## Qualification, energy and serialized evidence

Each contribution must independently preserve the certified physical plane
and any actual ring/disc axis. Existing complete point-inventory reflection
qualification remains available. A transverse component is not discarded;
unsupported requests fail. Even exactly cancelling out-of-plane electric and
gravity contributions are conservatively refused because this milestone does
not certify cross-contribution symmetry. The unchanged runtime domain checks,
source-jump guards and nonrelativistic speed limit remain active.

The existing controller receives the summed full-vector force and separate
energy terms through `EnergyBreakdown`. There is no new ODE algorithm.
The original electric-only branch remains unchanged when gravity is absent.

Active gravity exports use `test_charge_motion.v2` and
`test_charge_viewer.v2`. Every saved row retains electric and gravity force
vectors and potential energies separately. `potential_v` remains electric V;
`potential_energy_j` and the shared viewer's `interaction_energy_j` are the
complete U_e+U_g in v2. Total and drift include both contributions. The
comparison readout says **U_e + U_g**, not qV for their sum.

Validation reconstructs the exact built-in component, verifies each saved
force/energy contribution and the resultant independently, and rejects missing
or undeclared gravity. Scale-aware checks use physical magnitudes and floating
point roundoff, not an absolute macroscopic force/energy floor that would hide
proton-scale corruption. The drift calculation differences each energy
contribution independently. Nonfinite or unrepresentable gravity forces are
rejected; no absolute accuracy guarantee is asserted at extreme numerical
scales or under arbitrarily large energy gauges.

When gravity is absent, motion/viewer exports retain v1, omit the extra
contributions and preserve existing scenario identities. A pre-change legacy
fixture was compared byte-for-byte during development; regression tests also
check the old and zero-gravity limits.

## Viewer and reproduction

The existing canvas renderer, source drawing, time slider, play/pause/restart,
projection and graph functions are reused. An opt-in presentation extension
adds orange electric, blue gravitational and purple resultant force arrows
on **one common linear force scale** for each run. Zero force has no arrow;
velocity uses its own scale. The numerical ledger makes cancelling or
physically overlapping arrows explicit. The chart distinguishes K, U_e, U_g
and total energy. Coincident curves can overlap physically, so their saved
values remain in the readout. Nonaxial displays prefer upward opposite g;
world-axis labels still identify the actual projection.

```powershell
git pull --ff-only
python -m pip install -e ".[test]"
python examples/electric_gravity_motion.py --case jee2012-proton --output output/m21e-proton.html
python examples/electric_gravity_motion.py --case mass-revision --output output/m21e-mass.html
Start-Process .\output\m21e-proton.html
```

Every export is self-contained offline HTML with a detached JSON source/model
and trajectory audit. `tests/test_m21e_composed_forces.py` checks the physics,
limits, revisions, coordinate/reference invariance and corrupted records.
`tools/check_m21e_viewer.py` checks actual Chromium canvas force strokes,
visible energy/axis labels, controls, immutable saved data, 390px layout and
absence of network requests or JavaScript errors. Acceptance results belong
in the PR evidence, not an unverified pass-count assertion in this document.

## Deliberate boundaries

This combines uniform gravity with **prescribed, nonresponding electric
sources**. It does not add gravity to conductor-induced particle dynamics or
unify M21d's static connection backend with this motion model. It does not add
drag, terminal velocity, switched fields, magnetic force, reacting sources,
arbitrary force callbacks, unrestricted 3D motion or a neutral-particle motion
specification. An admissible revised model is not automatically a complete or
comparable trajectory; existing source-guard and exact-clock contracts apply.
