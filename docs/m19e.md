# M19e — Honest source identities and world-oriented fixed-field diagrams

## Motivation and scope

M19d's source-anchored *open* exploration of page 12 Q40–41 in
`02_conductors_half_size.pdf` identified a teaching discrepancy: the physical
rings share a **world-horizontal x-axis** while the generic M19b schematic
shows every ring/disc axis vertically, with anonymous `S1`, `S2` markers.
The trajectory and axial fields were **already correct**; the problem was
fidelity of presentation and source labeling, not a missing solver law.

M19e adds **two opt-in presentation inputs** to the existing
`sample_test_charge_viewer()` / `test_charge_slice()` path. It does not change
source charge distributions, M19a's force law `F=qE`, the full energy `U=qV`,
RK4 time integration, conductor induction, or static/sweep/M16–M18 viewers.
No scene graph or general scenario revision system is added.

## Authoring example

```python
from conductor_sim import sample_test_charge_viewer, integrate_test_charge

# `spec` is an existing TestChargeMotionSpec with fixed ring/disc sources;
# `result` is a matching, previously integrated TestChargeMotionResult.
result = integrate_test_charge(spec)
bundle = sample_test_charge_viewer(
    spec, result=result,
    axis_orientation='horizontal',
    source_annotations=(
        ('ring:A', 'Ring A'),
        ('ring:B', 'Ring B'),
        ('field:external', 'External field'),
    ),
)
```

This assumes those *three actual sources* were authored in precisely that
order. `source_annotations` accepts one `(stable_id, display_label)` pair per
physical source, validates unique bounded IDs, unique printable labels, source
kind and original array index, and refuses mismatches before exporting.
Source identity is **author supplied**, not inferred from charge, geometry or
index; using identical IDs for two different hypothetical scenarios remains
an author responsibility. The annotations are presentation/provenance only,
not a persistent engine registry or revision-lineage API. They do **not**
modify the public `PrescribedField` source inventory or the numerical result.

`axis_orientation='horizontal'` is allowed only when the physical model has a
certified ring/disc symmetry axis. The signed **actual world axis** becomes
screen right (`slice.u`). The vertical direction (`slice.v`) is the
right-handed perpendicular within the **already certified physical plane**.
The default `'vertical'` preserves the previous M19b plot orientation and
serialized bundle format exactly. A full-spatial model without any ring/disc
has no certified axial direction; requesting the new horizontal axial view
is refused rather than inventing an axis.

## What the learner sees

- The caption explicitly states what screen right/up mean in **world x/y/z**
  coordinates, including their signs. It also names the signed physical
  symmetry-axis direction. For non-cardinal directions, the full unit vector
  is shown; orientation is clearly a **schematic display choice**, not a
  dynamical constraint.
- Ring meridian intersections and disk diameters are drawn **perpendicular to
  their true physical axes** after projection. This is merely source geometry;
  ring/disc off-axis field or potential is neither evaluated nor painted.
- Diagram labels and the source-details inventory use exactly the author
  labels and stable IDs, safely rendered as canvas text / textContent.
  Source charges and uniform-field vector values remain visible with SI units.
- Axial displacement, velocity, potential and field profiles are projected
  along the **physical signed symmetry axis** (`prescribed.axis`), not whichever
  screen axis was chosen. Time samples, forces, energies and axial graph gaps
  are unaffected by the chosen orientation.
- The supplied 2D scene is a schematic view; it is **not** a FEMM slice,
  off-axis field map, proof of rigid ring mechanics, or a full 3D model.

## Source-faithful teaching example

```powershell
python -m pip install -e ".[test]"
python examples/ring_source_orientation.py --case field-off --output output/m19e-ring-A-B.html
Start-Process .\output\m19e-ring-A-B.html
python examples/ring_source_orientation.py --case axial-field --output output/m19e-axial-E.html
```

This example uses fixed, uniformly charged nonconducting rings A and B
(radius 0.30 m, world x-axis, centers x=0 and x=0.40 m) and one explicit
external uniform-field source. These are **teacher hypotheticals**: the
workbook's upward field exerts a transverse force, so free 1D axial motion
under the source-faithful field remains unsupported by the axial-only ring
model; the workbook also supplies a symbolic mass, not a numeric one.
The example changes the external field and stipulates 0.10 kg **explicitly**;
it does not imply these were original source facts. It preserves source IDs
(`ring:A`, `ring:B`, `field:external`) between the two scenarios.

## Verification and limitations

New tests check exact v1-default serialization against four **frozen**
accepted-M19b SHA-256 bundle digests, identity/order/kind binding, malicious
label escaping, corrupted-axis and metadata refusals, world-translated/tilted
axes, disc-surface null field values and conservation of numerical samples.
An accepted-source saved-data round trip may renormalize a tilted unit axis by
one binary ulp, giving a spurious energy-drift validation failure. The private
**verifier-only** reconstruction now retains the exact already-unit source
axis after bounding the normalization difference at `2e-15` and still
requires exact identity of all other serialized source fields. This does not
change production source or trajectory objects.

Real Chromium acceptance checks the **painted positions** of both meridian
intersections for each ring, source labels, world-axis caption, the original
M19b vector/time controls, graph cursors, mobile width, JavaScript errors and
network requests. Existing M19b and older viewer regressions remain gates.

This milestone does not implement a general 3D electric field of a ring/disc,
source-ID persistence across independently authored runs, a scene graph,
physical rigid ring constraints, browser-time physics, inverse problem solving
or simultaneous moving charge-induced redistribution.
